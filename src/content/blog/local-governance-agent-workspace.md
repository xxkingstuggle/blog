当你在同一台 Mac 上同时维护十几个项目，每天高强度开着 Codex 和 Claude Code 让它们帮你写代码的时候，如果没立下规矩，你的本地硬盘很快就会变成灾难现场。

我这么说，是因为下面这四幕血压飙升的现场，我全都亲身经历过。

第一幕是外层目录变成垃圾场。Agent 为了存一次打包产物或者留一份交接说明，随手在项目外层新建了 `releases/`、`handoff/`、`test-final-2/` 这种文件夹。过上两个礼拜再打开目录一看，满屏幕都是名字差不多的文件夹，根本分不清哪个是真代码、哪个能删。

第二幕更吓人。我有次拉了一个别人的开源仓库下来，在本地打补丁调试，结果 Agent 修完代码太积极，顺手敲了远端推送，差一点点就把别人的开源仓库直接推到我自己的 GitHub 名下去了。

第三幕发生在跨窗口接力的时候。上一个会话刚帮我把一个棘手的 Bug 修了一半，还没来得及 `git commit`；我新开了一个会话窗口进来，新 Agent 一眼看到工作区有未提交的 `diff`，居然自作聪明地以为那是上次测试留下的脏垃圾，二话不说一句 `git checkout -- .`，把我刚写完的半截心血当场抹得干干净净。

第四幕则是空头支票。Agent 在终端里跑过一次静态 `tsc` 编译没报错，就敢喜气洋洋地跟我汇报「功能已全部交付完成」。结果我点开浏览器页面一按按钮，连点击事件都没绑上去。

接连吃过这几次闷亏之后，我痛定思痛，把自己电脑上的目录落位规约、Git 安全红线和跨会话交接机制全部整理成了硬性的工程条款，打包成 [**local-governance-skill (v1.0.0)**](https://github.com/xxkingstuggle/local-governance-skill) 挂进了每个项目的启动上下文里。

我干的第一件事，就是把以前乱七八糟堆在同一个文件夹下的项目，按路径名立下了铁律。让任何 Agent 只要扫一眼当前的工作路径 `pwd`，不用问我，就能立刻明白这份代码是谁的、能不能往外推。

现在我把主目录下的 `~/Developer` 切成了三块清清楚楚的领地。

凡是我自己的正式开源或线上仓库，统一放在 `~/Developer/repos/github.com/xxkingstuggle/<repo>` 下，而且日常开发严格限制在当前项目根目录内，严禁跨目录去读写外层路径。

凡是拉下来学习或打补丁的他人开源仓库，必须按原作者名字放在 `~/Developer/repos/github.com/<owner>/<repo>`。规矩写死，只要路径里的 `<owner>` 不是 `xxkingstuggle`，天王老子来了也不准往我名下的远端仓库推。

至于纯本地不打算上传的私有工具，统一归置到 `~/Developer/repos/local/<name>`；一次性的数据清洗或者随手试探的实验脚本，全部丢进 `~/Developer/scratch/<name>`。本地编译打包出来的产物只准留在项目内部被 `.gitignore` 忽略的 `dist/` 或 `build/` 里；正式发版一律走 `gh release create` 托管到 GitHub Releases，永远不再创建任何外层 `releases/` 或 `handoff/` 目录。

目录理清之后，我在全局 `AGENTS.md` 和 Skill 里焊死了两条不准商量的安全红线。

第一条红线，删除本地文件一律移入 macOS 废纸篓（调用 `/usr/bin/trash` 或移至 `~/.Trash`），严禁执行 `rm -rf`。

道理特别简单，AI 再聪明，也有误判文件用途的时候。移进废纸篓的文件发现删错了，我点两下鼠标就能原样捞回来；要是让它跑了 `rm -rf`，删错了那是真的一滴渣都不剩。

第二条红线，严禁无脑执行 `git add .`。每次在本地 `commit` 或者往远端 `push` 之前，必须先核对 `.env`、私钥、Token、本地 SQLite 数据库以及大体积二进制文件有没有被 `.gitignore` 严密拦住；大改动必须先切独立分支，没拿到我明确的上线授权前，绝不擅自推主分支。

管住了手脚，接下来还要解决那个最常见的痛点，为什么新开一个 Agent 会话接手半截项目时，它总是像失忆了一样到处瞎猜？

我想了很久才想明白这件事。因为 `git log` 里面只记录了「已经写成功并提交上去的代码」，它从来不记录「刚才我们试过哪条路已经被证明走不通了」，也不记录「现在到底卡在哪个外部条件上」。

新会话一进来，看到代码停在半路，它不知道前因后果，自然就会把前一个会话刚踩过的死胡同又重新踩一遍。

为了治好这个跨会话失忆症，遇到需要跨多个窗口接力的大重构时，我让 `local-governance` 在项目里维护三个极简的 Markdown 状态账本。

| 文件名 | 记什么内容 | 什么时候更新 |
|---|---|---|
| `PROGRESS.md` | 当前分支的目标、已经跑通并提交的步骤、紧接着下一步要干什么 | 每完成一个自测通过的小步骤并本地 commit 时顺手更新 |
| `BLOCKED.md` | Agent 自己搞不定的外部卡点（比如需要插安卓真机测 USB、缺环境变量、需人工扫码） | 只有真遇到外部阻塞时才建，卡点解除后直接删掉 |
| `DECISIONS.md` | 关键的技术选型原因（比如为什么选了方案 B 而放弃了方案 A） | 做了重要架构取舍时记一笔，防止下一个会话进来又把废弃方案重写一遍 |

有了这三张薄薄的纸，新会话进来不用我费口舌把背景重讲一遍，读完 `PROGRESS.md` 和 `DECISIONS.md` 就能接着上一棒的脚印往下跑；看到 `BLOCKED.md` 就知道哪一步得等我插上真机或者填好密钥。

当然，我最讨厌为了规矩而搞形式主义。如果今天只是顺手改一两个样式文件的小活儿，根本不需要去建上面那三个文档，直接改完测通就完事。只有遇到新建工程、跨模块大重构、正式发版，或者进场发现工作区有来路不明的脏改动时，才按这套治理流程走。

但有一条底线是不分任务大小的，在跟我说「改完了」之前，必须实打实跑过类型检查、Lint（0 报错 0 警告）和自动化测试，改了前端界面还得附上真实的浏览器断言或截图日志。整套 `SKILL.md` 规范和交接模板我都已经发在了 [local-governance-skill v1.0.0 Release](https://github.com/xxkingstuggle/local-governance-skill/releases/tag/v1.0.0) 上，如果你也常被本地 Agent 的野蛮生长搞得头大，不妨直接拿去管管它们。
