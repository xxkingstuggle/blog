我想要的习惯打卡应用很简单：每天打开，看到今天要做什么，点一下就记录完成。

听起来没什么技术难度。但当我想把它放进 iPhone 桌面小组件，并且在 Mac 上也能使用时，问题就出现了。

**主 App 能读到的数据，小组件不一定能读到。小组件里点了打卡，主 App 也不一定立刻知道。**

仓库现已完成凭据隔离审计并在 GitHub 转为 Public（[**HabitBloom v1.0.0 源码 Release**](https://github.com/xxkingstuggle/HabitBloom/releases/tag/v1.0.0)，MIT 许可）。这篇文章讲清楚：它做到了哪里，为什么选择这些技术，以及我如何和 AI 一起把功能逐步接起来。

## 从一张卡片开始，而不是从账号系统开始

HabitBloom 使用 SwiftUI 做界面、SwiftData 管理本地习惯与打卡记录。每张习惯卡片可以配置名称、图标、颜色、执行周期和提醒，也能切换不同样式。

我优先做的是一天内真实会发生的操作：创建习惯、打卡、修改、查看连续天数和月度统计。系统通知负责提醒，日历可以补记或取消历史打卡。

相比先搭用户账号和完整云数据库，本地优先更符合它的使用场景：**简单记录不应该依赖服务器正常运行。**

## 难点不在卡片，而在小组件如何拿数据

WidgetKit 不是主 App 的另一个普通页面。它有自己的刷新时机和执行约束，不能直接把主 App 的 SwiftData 当成共享数据库使用。

所以我把要展示的习惯状态整理成更小的 **Widget 快照**。在 App Group 可用的安装环境中，小组件能读取本地共享数据；在某些侧载、重签名环境下，App Group 可能失效，项目另外准备了 Cloudflare Worker 的远端 HTTP 快照路径。

这不是同时让两个地方独立维护整份数据库，而是尽量让：

- **SwiftData 保存主数据**：习惯、打卡记录和本地操作；
- **快照提供展示状态**：小组件只获取它真正要显示的内容；
- **Widget 打卡再回并**：小组件产生的操作通过本地队列或远端路径，等待主 App 启动后合并回本地数据。

## 为什么不直接做一套「实时同步」？

因为这会改变整个项目的复杂度。

如果承诺多端实时同步，就要考虑设备同时修改、离线恢复、冲突解决、身份验证与长期维护。HabitBloom 目前最需要的是可靠的个人打卡与小组件展示，而不是完整的协作服务。

因此远程能力只覆盖两个较小的需求：**小组件状态快照与轻量文字备份**。

它的后端使用 Cloudflare Workers 和 Durable Objects。远端文字备份保存习惯配置、打卡日期等轻量数据，不把全部自定义图片直接塞进备份；小组件图片走单独的引用和上传路径。

没有配置服务器时，应用仍然可以作为本地习惯记录工具使用。

## AI 在开发中负责什么？

这个项目也体现了我使用 AI 编程的方式。

我先从实际使用问题确定功能范围，再借助 AI 工具参与界面、数据逻辑、组件集成和代码检查。关键不是 AI 生成了多少代码，而是功能最终能否对应到清楚的文件、数据流与验证方式。

项目把统计计算等与界面无关的部分抽成了核心模块，提供 Smoke 和 Stress 两类测试入口；还保留了 iOS 模拟器与 Mac Catalyst 的构建方法。

这意味着别人不仅能看到一张设计图，还能打开 Xcode 工程、检查 SwiftData 模型、Widget 扩展和 Worker 源码，理解功能是怎样组织的。

**不过，仓库提供测试命令不代表所有设备上的测试都已经通过。** 真实设备、侧载条件和长时间运行仍需要持续验收。

## 当前成品与还没做完的部分

代码中已有习惯卡片、提醒、统计、互动小组件、本地 JSON 导入导出和可选的远端快照路径。

但现阶段仍有明确边界：

- 暂无公开签名安装包或 App Store 版本，想体验需要从 Xcode 自行构建；
- 没有完整的多设备冲突解决界面，也没有 iCloud / CloudKit 同步；
- Widget 刷新时机受系统控制，不能保证每次操作都实时出现在其他设备；
- 图像卡片与不同侧载环境仍有需要补充的设备回归测试。

这些限制会写在项目页里，而不是藏到文章最后。

我从 HabitBloom 学到的一件事是：**把界面做出来只是起点；真正让软件能持续使用的，是数据如何保存、组件如何通信，以及失败时怎样退回可用状态。**
