HabitBloom 从卡片式习惯记录开始。主 App 的数据可以先放在本机，桌面小组件却需要另一条能拿到摘要的路径。免费签名与侧载条件，又让这件事多了一层约束。

这份案例记录当前源码采用的本地存储与远端快照方案。项目源码私有，暂时没有公开安装包。

## 先把数据留在本机

HabitBloom 用 SwiftData 保存习惯和打卡记录，WidgetKit 展示单项习惯、多项习惯和摘要卡片。项目也包含本地提醒、统计和可交互的日历。这个范围适合先把个人使用路径做出来，不需要一开始就依赖账号或完整云端同步。

小组件拿数据有两条路：正常共享环境可以读 App Group 快照；侧载环境下，项目还实现了 Cloudflare Worker 的远端 HTTP 快照。主 App 通过 HTTP 请求写入快照，小组件请求时尝试读取远端内容；请求失败时会回退到已有的缓存或本地 App Group 数据。它交换的是已经整理好的 Widget 状态，不是让 Widget 直接查询主 App 的 SwiftData。

小组件打卡也有对应的回并流程：Widget 记录操作，并尝试把更新后的快照发到远端；主 App 启动时会将待处理的 Widget 打卡合并回本地数据。代码里是 HTTP 请求与启动时回并，没有 WebSocket 通道，也没有完整的多设备冲突处理界面。

## 这条路径的边界

快照请求受网络和 WidgetKit 刷新时机影响。远端请求失败时，界面可能使用缓存或本地快照；不能把它描述成所有设备都能实时看到最新内容。多个设备同时编辑、离线期间的多次修改以及冲突如何呈现，也没有作为完整同步产品验证。

因此更准确的说法是：HabitBloom 用本地 SwiftData 保存主数据，并为 Widget 提供 App Group 与 HTTP 远端快照路径；主 App 在启动时回并部分 Widget 打卡。这是一项应用内的工程方案，不代表可靠的通用多端同步服务。

我负责定义功能边界、组织应用与 Widget 的数据路径，并检查集成后的实现。AI 工具参与了开发或检查；其输出需要回到源码、构建和相应测试核对。项目还使用 Apple 的 SwiftUI、SwiftData、WidgetKit，以及 Cloudflare Worker / Durable Objects 等平台能力，这些平台本身不归我所有。
