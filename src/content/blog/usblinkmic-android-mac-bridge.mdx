手机有现成的麦克风，也能接入网络；Mac 需要的是能被其他软件选择的音频输入，以及可用的网络接口。USBLinkMic 把两端之间的连接步骤收进一个面板，但音频、供网与系统权限仍是三件需要分别确认的事。

本文更新于 2026-10-23，链路说明依据公开 Release、对应 Git 标签和仓库文档。

## 一套 Mac 界面，三条不同的链路

USBLinkMic 的公开说明把它分成三项用途：Android 手机麦克风传到 Mac、手机通过 USB 网络共享给 Mac，以及 Mac 通过 Android VPN 与转发组件给手机供网。它们共用一个 Mac 应用入口，但依赖的系统能力不同；“插上线”并不代表三条链路都已经就绪。

麦克风路径通过 ADB 或同一可信局域网传输 Android 采集的声音。要让会议或录音软件选择手机作为输入，还需要把声音交给虚拟音频设备；项目使用 BlackHole 作为可选的外部组件，用户需自行安装。Wi-Fi 音频链路没有加密，不能在不可信的公共网络中使用。

手机给 Mac 供网依赖 Android 的 USB NCM 与系统共享能力。Mac 给手机供网则使用 Android VPN 接口和 Gnirehtet 转发组件。两种供网方向互斥；Android 版本、厂商系统和 macOS 网络服务都会影响可用性。Gnirehtet 与 BlackHole 都是第三方项目，来源和许可应按各自记录查看。

## 集成边界比功能清单更有用

公开仓库把配套 Android APK、ADB 和 Mac 端运行所需组件放进 Mac 安装包，减少用户另行准备开发工具的步骤；USB 调试、录音与 VPN 等系统授权仍需要用户自己确认。BlackHole 不随应用自动安装。

项目也区分“链路已经连接”和“互联网一定可用”。手机网络接入 Mac 后，macOS 仍可能优先使用 Wi-Fi；应用显示链路状态，不会替用户重排系统网络优先级。这个边界能避免一个绿色状态被误读为整条网络路径都已验收。

## 发布记录不等于全场景通过

本文讨论的是公开标签及其 Release 对应的项目记录。当前公开版本、正在开发的源码版本和已安装应用可能不同；下载与可用版本请以 [USBLinkMic 作品页](/software/usblinkmic/) 的当前状态为准。

仓库的验收文档把测试项与自动化下层证据、待实机检查分开记录。它没有宣称跨 ROM、长时间运行、反复插拔以及复杂网络组合都已通过。因此，源码中的生命周期处理、自动化测试和一次界面截图，都不能单独证明所有手机上稳定可用。

我负责需求判断、范围取舍，以及把 Mac、Android 与系统组件接进一条可检查的流程；AI 工具参与开发和审查，结果仍要由项目证据核对。本文不声称每段代码都由我独立从零编写，也不把 BlackHole 或 Gnirehtet 的实现归为个人成果。
