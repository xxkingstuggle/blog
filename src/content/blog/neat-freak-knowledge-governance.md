用 AI Agent 高频改代码时，最容易失控的不是代码本身，而是**代码改完了，周围的文档和记忆全成了误导人的假信息**。

我自己在项目里就吃过好几次亏：

- 代码里早就把本地监听端口从 `8080` 改成了 `15151`，但 `README.md` 和 `INSTALL.md` 里还写着 `8080`；
- 某条阻碍打包的 Bug 昨天就已经修好发版了，但项目的 `BLOCKED.md` 或者 Agent 的历史记忆里还记着“该项目因编译报错暂停”；
- 过两天新开一个会话让 AI 加功能，它一上来先读了过期的文档和旧记忆，顺着错误的假设把已经跑通的逻辑又改坏了。

为了解决这个收尾问题，我给自己写了一个叫 **洁癖（Neat-Freak）** 的本地 Skill，专门在阶段性开发结束、准备发版或切到别的项目之前跑一遍。

## 不新造总结文档，只留一份能对上代码的说明

很多时候让 AI “整理文档”，它最喜欢干的事是在目录里再新建一份 `SUMMARY_FINAL.md` 或者 `ARCHITECTURE_V2.md`。结果一个仓库里同时躺着三份不同时期的说明，下一次进来更分不清哪份是真的。

所以我在 `neat-freak` 里定了一条死规矩：**不准靠新建一堆总结文件来交差，直接在原文件上改，删掉过期内容，让每个问题只留一处现役说明。**

## 收尾时具体核对哪六件事

每次唤起 `neat-freak` 时，它会先跑一遍只读盘点脚本（`scripts/audit-inventory.sh`），然后逐项核对下面这六个地方是不是能对上号：

| 检查位置 | 具体核对什么 | 以什么为准 |
|---|---|---|
| **1. 源码与配置** | 现在的版本号、启动脚本、环境变量和默认端口到底是什么？ | `package.json`、`Package.swift`、`Info.plist` 和真实入口代码 |
| **2. 本机实际运行态** | `/Applications` 里装的 App、后台跑的守护进程或容器，跟刚改完的源码是不是同一个版本？ | 进程状态、应用 `Info.plist` 版本号、接口实测返回 |
| **3. 项目文档** | `README.md`、`PROGRESS.md` 里有没有写着已经删掉的命令或旧截图？ | 对照源码逐条删改，合并重复文档 |
| **4. `AGENTS.md` / `CLAUDE.md`** | 规则文件里写的 `check` / `test` / `build` 命令还能不能跑通？ | 现场在终端跑一遍，跑不通就修规则 |
| **5. Agent 跨会话记忆** | 记忆库里记的项目状态、是否开源、最新 Release 版本是不是已经过期了？ | 对照最新的 `git log` 和 GitHub Release 更新记忆笔记 |
| **6. 工作区残留** | 目录里有没有没提交的测试截图、临时脚本或已经合并完的旧分支？ | `git status`，没用的临时文件统一移进 `~/.Trash` |

## 文档和代码打架时听谁的

排查过程中经常会发现文档、记忆和代码互相矛盾。这时候判断谁对谁错的顺序很简单：

```text
实际跑通的测试与运行态  ＞  当前主分支源码与配置  ＞  Git 提交与 Release 记录  ＞  项目文档  ＞  历史记忆
```

只要新代码跑通了测试，就按新代码去改文档和记忆，绝不反过来拿过期的旧文档去质疑已经验证通过的代码。把旧描述删干净、跑通一遍项目的构建和测试命令，一次收尾就算完成。
