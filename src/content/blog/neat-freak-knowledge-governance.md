用 AI Agent 高频写代码的人，迟早都会撞上一个比代码报错更让人窝火的怪象。

代码明明已经跑得飞快了，结果散落在仓库四周的文档和 AI 历史记忆，全都变成了误导人的假情报。

我自己在维护手头十几个项目的时候，就接连被这些过期情报背刺了好几回。

有一回，我早在三天前就把下载器的本地监听端口从 `8080` 改成了 `15151`，测试全过了，包也发了，但我忘了去改仓库根目录的 `README.md` 和 `INSTALL.md`，那两份文档里还大摇大摆地写着 `8080`。

还有一回，某个卡住打包的签名 Bug 我头天晚上就已经修通发版了，但项目里的 `BLOCKED.md` 还有 Agent 跨会话记忆库里，还留着一句「该项目因编译报错暂停开发」。

最要命的后果发生在两天后。当我新开了一个 Codex 会话窗口，想让它顺手帮我加个小功能时，它一进场很乖巧地先去读了文档和旧记忆。读完之后，它居然信了那些过期的假情报，顺着错误的旧假设动手，把我已经跑通的新代码又给改回去了。

那一刻我看着屏幕上的 `git diff`，真是哭笑不得。

为了不让过期的文档继续在仓库里埋雷，我专门给自己写了一个叫「洁癖（Neat-Freak）」的本地收尾 Skill。每当一个阶段的功能开发结束、准备发版，或者我准备合上这个项目切去干别的活儿之前，就唤起它做一次彻底的大扫除。

在写这个 Skill 的时候，我先堵死了 AI 整理文档时最爱犯的一个臭毛病。

如果你平时直接跟 AI 说一句「帮我整理一下项目文档」，它九成九最喜欢干的事，就是在你的目录里再新建一份叫 `SUMMARY_FINAL.md`、`ARCHITECTURE_V2.md` 或者 `HANDOFF_NEW.md` 的文件。

它觉得自己新建了一份完美总结就算交差了。结果你的仓库里同时躺着三份不同月份写的架构说明，等下一次新会话进来读代码的时候，看到三份互相打架的文档，脑子比以前更乱。

所以我在 `neat-freak` 里立下的第一条死规矩就是，严禁靠新建总结文件来交差。除非我明确开口要求新建，否则一律只能在原有的现役文档上原地动刀，把过期作废的段落狠心删掉，保证每一件事在整个仓库里只有唯一一处真实说明。

每次我在终端里把 `neat-freak` 叫出来，它不会上来就乱改文件，而是先跑一遍只读盘点脚本 `scripts/audit-inventory.sh`，然后拿着放大镜逐一核对下面这六个地方到底对不对得上号。

| 检查位置 | 具体核对什么 | 以什么为准 |
|---|---|---|
| 1. 源码与配置 | 现在的版本号、启动脚本、环境变量和默认端口到底是什么 | `package.json`、`Package.swift`、`Info.plist` 和真实入口代码 |
| 2. 本机实际运行态 | `/Applications` 里装的 App、后台跑的守护进程或容器，跟刚改完的源码是不是同一版 | 进程状态、应用 `Info.plist` 版本号、接口实测返回 |
| 3. 项目文档 | `README.md`、`PROGRESS.md` 里有没有写着已经删掉的命令或旧截图 | 对照源码逐条删改，合并重复文档 |
| 4. `AGENTS.md` 与 `CLAUDE.md` | 规则文件里写的 `check`、`test`、`build` 命令还能不能跑通 | 现场在终端实跑一遍，跑不通就修规则 |
| 5. Agent 跨会话记忆 | 记忆库里记的项目状态、是否开源、最新 Release 版本是不是已经过期了 | 对照最新的 `git log` 和 GitHub Release 更新记忆笔记 |
| 6. 工作区残留 | 目录里有没有没提交的测试截图、临时脚本或已经合并完的旧分支 | `git status`，没用的临时文件统一移进 `~/.Trash` |

在逐项对账的过程里，最常遇到的情况就是，文档里写的一套、记忆库里记的一套、代码里跑的又是另一套。三方打架的时候到底该听谁的？

我给它排了一条不可动摇的真相优先级链条。

```text
实际跑通的测试与运行态  ＞  当前主分支源码与配置  ＞  Git 提交与 Release 记录  ＞  项目文档  ＞  历史记忆
```

只要新的源码已经实打实跑通了自动化测试和运行态验证，那就毫不犹豫地按新源码去改写文档和记忆，绝不允许反过来拿一本过期的旧文档去质疑已经验证通过的代码。

等把所有过期的文字描述和作废的 `BLOCKED.md` 清扫干净，再重新跑通一遍项目的构建和测试门禁，确认工作区干干净净，一次项目的收尾才算真正画上句号。毕竟对于长期靠 AI 协作维护的仓库来说，删掉一句过期的假话，往往比多写一百行新代码更有价值。
