在高频使用 AI Agent 迭代项目的过程中，有一个几乎所有开发者都会踩的坑：**代码跑得飞快，但项目的知识面（README、架构文档、`AGENTS.md`、跨会话记忆）却在迅速腐烂。**

最典型的症状是：

- 代码里早就把端口从 `8080` 改成了 `15151`，但 `README.md` 和 `INSTALL.md` 里还写着旧端口；
- 某项阻碍发版的 Bug 昨天已经修好并合入 `main`，但 `BLOCKED.md` 或 Agent 的长期记忆里还记着“该项目因网络错误不可用”；
- 下一次开启新会话时，AI 先读了过期的文档和记忆，结果顺着错误的假设把已经修好的代码又改坏了。

为了解决这个“最后一公里”的知识腐败问题，我设计并迭代到了 `v3.1.1` 的核心收尾技能：**洁癖（Neat-Freak — Knowledge and Governance Closeout）**。

## 一、核心定位：目标不是“多写文档”，而是“只留唯一现役答案”

很多文档整理工具的思路是“追加”——每次开发完再生成一份总结文档。结果项目里既有 `architecture.md`，又有 `architecture-v2.md`、`final-summary.md`，后人或下一个会话根本分不清哪份才是当前生效的事实。

`neat-freak` 的第一原则是**消歧与减法**：

> 让代码、真实运行态、项目文档、Agent 规则文件、获准维护的记忆和工作区状态彼此一致，让下一次会话或第一次接手的人能直接找到**唯一现役答案**。

## 二、六大事实面（Fact Surfaces）的收尾完成合同

在 `neat-freak` 中，一次知识收尾绝对不是简单润色一下 Markdown 排版，而是必须逐一核对并闭环以下**六个事实面**：

| 事实面 | 核心核查问题 | 采信的权威证据 |
|---|---|---|
| **1. 源码与配置面** | 当前导出的接口、版本号、脚本入口和默认参数到底是什么？ | `package.json`、`Package.swift`、`Info.plist`、真实入口源码 |
| **2. 真实运行态面** | 本地安装的应用、守护进程、容器或线上部署版本与当前源码一致吗？ | 进程状态、`/Applications` 元数据、健康检查接口、构建指纹 |
| **3. 项目文档面** | `README.md`、`INSTALL.md`、`PROGRESS.md` 是否还残留已废弃的命令或过期结论？ | 逐条对照源码与实跑输出，删除过期段落，合并重复文档 |
| **4. Agent 规则面** | 项目级 `AGENTS.md` / `CLAUDE.md` 里的构建命令、目录结构与禁令是否仍然准确？ | 实际执行其中声明的 `check` / `test` / `build` 命令验证 |
| **5. 跨会话记忆面** | Agent 记忆库中关于该项目状态、可见性、最新版本的条目是否已落后于事实？ | 核对最新 Git Commit 与 GitHub Release，原地覆写过期记忆 |
| **6. 工作区残留面** | 是否有未跟踪的临时产物、调试截图或废弃分支留在目录里？ | `git status --porcelain`、`git branch`，将无用临时物移入废纸篓 |

## 三、先盘点、后动刀：基于证据的冲突裁决优先级

当发现文档、记忆和代码互相矛盾时，`neat-freak` 严格遵循以下**事实裁决顺位**：

```text
真实运行态与自动化测试输出  ＞  当前主分支源码与配置  ＞  Git 提交与 Release 历史  ＞  项目文档  ＞  历史记忆
```

也就是说，**绝不能为了迎合旧文档而去怀疑已经通过测试的新代码，更不能凭旧记忆覆盖新事实**。

在具体执行时，`neat-freak` 会先运行只读盘点脚本（`scripts/audit-inventory.sh`），枚举工作区内的规则文件、状态账本、未提交变更与符号链接，列出所有“不一致项（Drift Items）”；然后原地更新现役文件、归档或清理过期文件，最后再次跑通项目的验证命令确认没有引入任何破坏。

正是依靠这套收尾合同，我才能在同时推进十余个跨端项目时，保证每个仓库在任意时刻打开都处于“代码、文档、记忆与发版状态四面合一”的干净状态。
