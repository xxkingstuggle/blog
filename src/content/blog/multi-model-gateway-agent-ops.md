平时在终端里同时开着 Codex CLI、Claude Code 还有桌面客户端写代码的人，只要手头的模型渠道稍微多一点，肯定都体会过那种配置散落一地的狼狈。

我前阵子就是这样。手头既有按量计费的官方 API Key，又有好几个需要走 OAuth 动态刷新的订阅账号（像 Google AI、Claude 还有国内的 WorkBuddy），全都零零散散地填在不同工具的配置文件里。

直接让各个客户端各自去连上游，用起来简直处处是雷。

最让人脑仁疼的是参数不兼容。比如 Codex CLI 发请求的时候，默认喜欢带上 `reasoning_effort` 字段，有时候还会传 `xhigh` 或者 `max` 这种高阶档位。结果有些上游兼容层脾气特别暴躁，一收到自己不认识的参数值，它连个正经的 `HTTP 400` 参数错误都不报，直接在服务端崩一个 `HTTP 500` 甩回来。

更别提哪条线路突然触发了 `429` 速率限制，我就得停下正在想的代码逻辑，去翻配置文件手动切账号；万一本地转发容器升级配置时不小心改崩了，桌面上正在跑的几个编码窗口瞬间全军覆没。

为了把手里所有的模型账号和私有渠道彻底收口到一个稳当的本地入口，我把市面上主流的三个开源网关 New API、Sub2API 和 CLIProxyAPI（简称 CPA）全在本地搭起来真刀真枪跑了一轮。

这三款工具用下来，脾气和侧重点的差别其实非常明显。

| 工具 | 适合干什么 | 我实际用下来的痛点或优势 |
|---|---|---|---|
| New API | 多人共用分发 Key、统计额度、配标准 OpenAI 渠道权重 | 后台面板很全，但遇到需要深度改写请求体或自己维护复杂 OAuth 握手的私有渠道，得去改核心代码 |
| Sub2API | 把网页或客户端订阅账号快速转成标准接口 | 足够轻，但路由编排和自定义扩展能力比较简单 |
| CLIProxyAPI (CPA) | 给本地 CLI 与 IDE 编码工具做协议转换与 OAuth 托管 | 支持挂载 Go `c-shared` 动态库插件，能把私有渠道（如 WorkBuddy、QoderWork）拆成独立插件维护，不污染主程序 |

试完这一圈，我最终定下了现在的双层架构。底下在 OrbStack 容器里跑 `CLIProxyAPI`（也就是 `cpa-local`），专门负责脏活累活，比如 OAuth 自动续期、[Go 动态库插件加载](/posts/cpa-go-abi-provider-plugins/)和底层协议清洗；而在最外层，则用我本机的 Magpie 统一管理路由组顺位和客户端可见性。哪条主线路突然 `429` 限流或者挂了，外层瞬间无感切到同组的候补线路上，终端里的编码任务连顿都不会顿一下。

架构立起来之后，我很快就遇到了前面提过的那个经典暗坑，OpenCode Zen 等第三方渠道偶发报 `HTTP 500` 的问题。

那几天特别邪门，平时随手发两句短对话测试，通道顺畅无比；可只要一让 Codex 跑真正的长编码任务，跑着跑着就会突然卡住半分钟，然后炸出一个 `500 Internal Server Error`。

我把网关抓到的原始请求体和响应体拉出来一比对，哭笑不得地发现了两件事。

第一件事是上游服务端太脆弱。当 Codex 请求里传过来的 `reasoning_effort` 档位超出了那个上游模型认识的枚举范围时，上游没写友好的参数校验，直接在内部抛异常崩了 `500`。

第二件事更蠢，是客户端的默认重试逻辑帮了倒忙。客户端一看到返回码是 `500`，满心以为是服务端临时网络抽风，于是拿着一模一样的非法参数，在原地乖乖做起了指数退避重试。连撞三次南墙、白白卡死半分钟之后才彻底报错放弃，连切去备用线路的机会都没给。

摸清病因之后，我在网关适配层连下了三刀。

第一刀是转发前参数预清洗。网关内部维护了每个目标模型真实支持的参数枚举表，在请求发往上游之前，自动把目标模型不认识的 `reasoning_effort` 字段裁剪掉，或者降级映射成它能吃得下的合法档位（比如统一收拢到 `high`）。

第二刀是单渠道代理彻底隔离。以前偷懒读全局的 `HTTP_PROXY` 环境变量，结果为了伺候某一个海外渠道改了代理配置，把原本应该直连的国内低延迟渠道也一块儿带进了沟里。现在我给每个需要走特定代理的渠道单独初始化独立的 `http.Transport` 实例，直连的归直连，过代理的归代理，井水不犯河水。

第三刀则是教会故障转移层分辨「真抽风」和「硬错误」。只有遇到 `429` 限流、`502`、`503` 网关抖动或者底层 TCP 连接重置时，才允许在当前节点重试；只要撞上 `400`、`401`、`403`，或者带有特定参数异常签名的 `500`，当场判定当前节点不可用，一毫秒都不耽误，直接切去同组的下一条候补线路。

把流量治理顺了，最后还有一个运维上的心腹大患，怎么做到天天自动跟进上游更新，却又绝对不会在一大早把我自己正在用的网关搞崩？

因为上游 `CLIProxyAPI` 和我自己的渠道插件都在高频迭代，如果写个无脑定时脚本，每天直接在现役容器里拉最新代码重编译覆盖，万一哪天上游半夜合入了一个破坏性提交，我第二天早上九点坐到电脑前准备写代码时，面对的就是一个彻底瘫痪的网关。

为了让自己每天早上都能安心喝口水直接干活，我写了一套每天上午 `09:00` 准时触发的蓝绿升级与自动回滚脚本。

脚本醒来后的第一步，是先去拉取上游源码和插件仓库状态，比对当前正在跑的容器 Commit SHA。如果两边代码根本没变，而且现役容器健康检查全绿，脚本直接静默退出，绝不瞎折腾。

一旦发现有新提交，它绝不会去碰正在跑的现役二进制文件，而是先在独立的临时构建目录里，把新版主程序和 `.so` 动态库插件编译打包成一个全新的候选镜像。

紧接着是最关键的真枪实弹验活。脚本会拿这个新镜像在旁路拉起一个候选容器，先后向它发射两枚真实探针，先调 `/v1/models` 检查所有插件有没有挂载成功、动态模型表有没有拉全；再发一次真实的最小流式对话请求，确认 Token 续期和 SSE 数据流能完整跑通。

只有这两枚探针全部返回绿灯，脚本才会把流量切到新容器上，同时把刚刚退下来的上一版好用的镜像打上保底标签（比如 `cpa-local:8.1.1`）留在本地，顺手清掉更早的悬空旧镜像。反过来，如果在编译或者探针验活的任何一步出了岔子，脚本会立刻销毁候选容器，毫秒级回退到上一版稳如泰山的旧镜像上，只把报错详情安静地写进运维日志里等我有空再看。

自从这套网关和早间自动巡检跑起来之后，我已经很久没有操心过「今天哪个模型账号限流了」或者「哪个 CLI 传错参数报错了」这种破事。对于每天靠 AI 工具写代码的人来说，最好的基础设施就是你平时根本感觉不到它的存在。
