跟 AI 搭档写过前端界面的人，一定都被它那种自信满满的汇报忽悠过。

你让它去改一版页面样式，它在终端里噼里啪啦改完 CSS，顺手跑了一遍 `tsc` 类型检查和 `astro build`，看到绿色的构建成功提示，甚至还贴心地截了一张小小的桌面端缩略图给你，拍着胸脯汇报「视觉升级已全部完成」。

表面看好像真挺完美。

但只要你留个心眼，亲自打开 Mac 上的 Safari 浏览器切一下暗色模式，或者把窗口拉到 `390px` 的 iPhone 宽度伸手点一下搜索框，假象就会在三秒钟之内碎一地。

暗色模式下的主按钮不知道什么时候退化成了刺眼的白底配浅灰字；左侧磨砂导航栏里弹出来的主题菜单，右边生生被容器的 `overflow` 齐根切掉了半截；卡片外框和里面图片的圆角拧成了厚薄不均的三层白边；更离谱的是，在 iPhone Safari 上手指刚点进搜索框，整个网页突然被系统强行放大了一圈，失焦之后还缩不回去。

在被这种「AI 觉得改好了、真机一碰就碎」的视觉回退折腾过好几轮之后，我彻底放弃了靠肉眼抽查和在提示词里苦口婆心叮嘱的做法。

我干了一件特别轴的事。我把所有容易退化的审美标准和交互红线，全部翻译成了冷酷无情的数学公式，写进了 `scripts/verify-studio-webkit.mjs` 和 `scripts/verify-iteration-webkit.mjs` 的 Playwright WebKit 自动化断言里。

今天你打开 `scripts/verify-studio-webkit.mjs` 看，里面写下的每一条 `assert`，背后几乎都是我真真切切踩过的一次视觉翻车事故。

第一场事故出在暗色模式的对比度偷懒上。

有一次改完关于页和作品卡片的按钮样式，亮色模式下看着白净素雅，一点毛病没有。结果一切到暗色模式，两处辣眼睛的 Bug 直接跳了出来，一处是原本该保持半透明磨砂质感的侧栏和卡片，因为样式优先级覆盖，直接退化成了死白死白的不透明色块 `rgb(255, 255, 255)`；另一处是正文里的超链接继承了亮色模式下的深海军蓝 `rgb(23, 32, 57)`，趴在深灰色的夜幕背景上，得把脸贴到屏幕上才看得清写的是啥。

还有一次，AI 为了图省事做暗色适配，居然直接给卡片加了一层 `filter: brightness(...)` 滤镜，把整张卡片弄得像蒙了一层脏雾。

从那以后，我直接让脚本在真实的 WebKit 内核里依次切过 `light`、`dark` 和 `system` 三种模式，现场调用 `getComputedStyle` 扒出渲染后的真实 RGB 通道数值，直接按 WCAG 相对亮度公式算对比度。

```js
const contrastRatio = ({ fg, bg }) => {
  const a = relativeLuminance(fg);
  const b = relativeLuminance(bg);
  return (Math.max(a, b) + 0.05) / (Math.min(a, b) + 0.05);
};
assert.ok(lightRatio >= 4.5, '亮色主按钮对比度必须 >= 4.5:1');
assert.ok(darkRatio >= 4.5, '暗色主按钮对比度必须 >= 4.5:1');
```

不仅对比度必须硬性跨过 `4.5`，脚本还会同时检查暗色文字卡片必须重新绘制深色渐变且 `filter` 必须等于 `none`，侧栏背景必须维持真正的 `rgba(...)` 半透明通道。以后不管谁改 CSS，只要敢拿全局滤镜糊弄暗色模式，或者不小心把哪个背景覆盖成了死白块，验收脚本一秒钟就会报错红灯。

第二场事故则关乎强迫症级别的几何美感，双层同心圆角。

本站首页的作品卡片是由外层容器 `.gallery-card`、内层视觉舞台 `.gallery-card-visual` 以及最里面的图片或视频嵌套组成的。AI 写样式的时候，特别喜欢拍脑袋给外层设一个 `border-radius: 16px`，给内层也设一个差不多的圆角，再给最里面的 `<img>` 又叠一层圆角和内边距。

这三个差不多凑在一起，卡片四个拐角处的留白就会出现肉眼可见的「两头厚、中间薄」，看着就像劣质塑料壳没套准一样别扭。

其实在光学和几何设计里，双层嵌套容器要想看着舒服，铁律只有一条，外层圆角半径减去中间的内边距，必须精确等于内层舞台的圆角半径（$R_{\text{outer}} - P_{\text{inset}} = R_{\text{inner}}$），而且最里面的图片自己绝对不能再画蛇添足加第三道圆角或内边距。

与其每次改完拿肉眼去盯拐角，我直接把这条几何铁律写成了像素级断言，误差连 `0.75px` 都不准超。

```js
assert.ok(
  Math.abs(media.outer - media.inset - media.inner) < 0.75,
  '外框与内层舞台必须保持同心圆角'
);
assert.ok(
  media.imageRadius < 0.2 && media.imagePadding < 0.2,
  '图片自身不能引入第三层圆角或内边距'
);
```

第三场事故是 WebKit 特有的磨砂容器裁切陷阱。

在桌面端左侧那条常驻的磨砂玻璃侧栏里，有一个点开切换亮暗主题的弹出菜单。在 Chrome 里有时候看着正常，但一进 Safari 的 WebKit 内核，因为外层侧栏同时带着 `backdrop-filter`、固定宽度和滚动裁剪属性，如果你把弹出菜单直接挂在侧栏的 DOM 节点底下，菜单往右展开的那一刻，超出侧栏宽度的右半边就会被齐根一刀切掉。

为了再也不犯这个错，我在脚本里模拟了桌面端和 `390px` 移动端的真实点击，死死断言弹出来的菜单必须通过 Portal 作为 `body > .theme-menu-popover[data-theme-floating]` 直接挂在根节点 `body` 底下，而且它展开后的 `getBoundingClientRect()` 四条物理边界，必须完完整整落在当前视口 `>= 5px` 的安全边距以内。

第四场事故则是老生常谈、但 AI 十次有九次会忘的 iPhone Safari `16px` 输入框红线与底部悬浮栏避让。

在桌面大屏上，把搜索框的字号设成 `13.5px` 看着确实精致秀气。但只要到了 iPhone Safari 上，用户手指头一旦点进计算字号小于 `16px` 的 `<input>` 或者 `<textarea>`，iOS 系统就会自作主张把整个网页猛地放大一截，而且你输完字收起键盘它都不会自动缩回去。

同理，移动端最底下有一条固定悬浮的毛玻璃导航栏 `.studio-mobile-dock`。如果页脚没有预留够充足的底部内边距，滑到页面最底下时，那个大号的 `MYZJX.` 品牌字标就会被悬浮导航栏严严实实挡住半截。

现在这两条也全成了移动端 WebKit 测试里的铁门禁，窄屏下所有可聚焦输入框的计算字号必须 `>= 16px`，所有导航触控按钮的热区高度必须 `>= 44px`，页脚的底部留白必须严格大于 `dockHeight + dockBottom + 16`。

自从把这些视觉、几何还有私人空间的状态流（比如在浏览器里用 Mock 路由模拟第二台设备抢先写库触发 `HTTP 409` 冲突、验证 `localStorage` 未同步草稿在刷新后自动恢复）统统焊进自动化脚本之后，我和 AI 协作改界面的速度不仅没变慢，反而快了一大截。因为我再也不用每次改完一行 CSS，就自己像个人肉测试员一样把几十个页面和亮暗模式点上一遍。

不过话分两头说，到了最后我还是得坦诚交代一句，Playwright WebKit 断言全绿，依然不等于真机验收完成。

自动化脚本里的模拟接口能证明前端状态机和 `tests/worker/security.test.ts` 里的后端契约严丝合缝，但它替代不了线上真实的 GitHub OAuth 跳转和 Cloudflare D1 的生产数据库迁移；脚本能把 `Math.abs(dividerY - footerY) < 1.5` 的线条对齐和颜色对比度算到小数点后两位，但它依然替代不了真实 iPhone 握在手里时的滑动阻尼、软键盘弹起那一刻的视口挤压感，以及人眼通读一篇文章时的呼吸节奏。

让不知疲倦的几何断言替我守住那些「绝对不能倒退」的工程下限，把我自己省下来的精力拿去抠真正决定质感的版式与文字，这才是我跟 AI 磨合到现在最舒服的分工。
