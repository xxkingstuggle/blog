我在本地用 `CLIProxyAPI` 搭多模型网关的时候，心里一直有个执念。我想把腾讯的 WorkBuddy（也就是 CodeBuddy CN）和阿里的 QoderWork 这两个渠道也接进来，统一洗成标准的 OpenAI 和 Anthropic 接口，喂给我本地的编码工具调用。

最开始我的做法特别简单粗暴，直接把上游网关的仓库 fork 了一把，在主程序源码里硬塞了两个新渠道。

刚跑通的那两天确实挺爽。但过了不到一个月，我就被日常维护折磨得苦不堪言。

因为这两个私有渠道根本不是换个 URL 那么简单。它们各自有一整套私有的 OAuth 登录流、后台心跳续期逻辑和专属的 SSE 流式响应结构，写下来的代码量相当可观。结果上游 `CLIProxyAPI` 更新又特别勤快，人家隔三差五重构一次核心包、发个新版本，我这边执行 `git merge` 的时候就会爆出一大片红彤彤的代码冲突。

解过三次一模一样的合并冲突之后，我把键盘一推，决定彻底换条路走。

我不再去污染上游主仓库的一行业务代码，而是单独建了一个叫 [**cpa-plugin**](https://github.com/xxkingstuggle/cpa-plugin) 的仓库，把这两个渠道剥离出来，编译成独立的 `.so` 和 `.dylib` 动态链接库，在运行时直接挂载到网关上。

听到用 Go 写动态库插件，很多写 Go 的朋友第一反应肯定是，你直接用 Go 标准库自带的 `plugin` 包不就行了吗？

说真的，谁在生产或者长期维护的项目里用过 Go 原生 `plugin` 包，谁就知道那玩意儿有多娇气。

Go 原生的 `plugin` 要求宿主主程序和插件必须使用分毫不差的同一个 Go 编译器小版本构建；不仅如此，两边 `go.mod` 里引用的任何公共第三方库版本、哪怕是编译时的工程路径有一丁点对不上，加载的时候就会直接甩给你一句冷冰冰的 `plugin was built with a different version of package`，当场罢工。

如果用原生 `plugin`，那上游网关每升一次依赖，我还是得跟着重新对齐全套 `go.mod` 重编，等于换汤不换药。

那怎么才能让插件跟宿主网关的 Go 版本和依赖树彻底解耦呢？

我选了一招老派但极其稳当的方案，用 `go build -buildmode=c-shared`，走最底层的 C ABI。

跨过边界的时候，宿主和插件之间绝不传递任何 Go 语言内部的 `struct`、切片或者接口指针，只认一套固定死签名的 C 函数导出表，在边界上只传最纯粹的 UTF-8 JSON 字符串指针和字节长度。

而且为了防止跨 CGO 边界出现内存泄漏，凡是由插件内部在堆上分配并返回给宿主的 C 字符串，统一由插件显式导出的 `FreeString` 函数负责回收释放。

这一层 C ABI 隔开之后，世界瞬间清净了。只要这几个 C 函数的签名不变，不管上游网关怎么升级 Go 编译器版本、怎么大改内部的依赖库，我编译好的动态库插件挂上去就能直接跑，再也不用解半行合并冲突。

把架构边界切干净之后，我在 `workbuddy/` 和 `qoderwork/` 这两个插件模块内部，集中火力干掉了三件最棘手的脏活。

第一件脏活是 OAuth 登录态的并发续期。这两个渠道都走 OAuth 认证（同时我也兼容了在无界面服务器环境直接传 PAT Token 的模式）。麻烦在于它们的 Access Token 过期时间很短，而我本地的 Codex CLI 一跑起多智能体任务，经常是三四个子协程在同一毫秒并发打过来。

如果不加控制，三四个并发请求同时发现 Token 快过期了，就会拿着同一个 Refresh Token 一窝蜂冲上去调刷新接口。第一个请求刷新成功把旧凭证作废了，后面紧跟着的三个请求当场就会收到 `401 Unauthorized` 报错，导致正在跑的代码任务半路夭折。

为此我在插件的 Token 管理层加了一把严格的并发互斥锁（Singleflight 双重检查）。一旦检测到 Token 临近过期窗口，只放行第一个拿到锁的协程去调上游刷新接口并原子写盘，同时到达的其他并发请求老老实实在锁外排队，等刷新落盘完成的下一毫秒直接拿新 Token 继续发请求，外部客户端完全无感。

第二件脏活是动态拉取账号真实的可用模型表。用过这类编程助手渠道的人都知道，你账号里到底能调哪些模型，经常跟着账号等级或者服务端的灰度策略变来变去。如果在代码里写死一张静态模型表，上游刚灰度的新模型你用不上，上游悄悄下线的旧模型你调了就报错。所以我让插件在启动和周期性巡检时，直接去调上游真实的枚举接口，把当前账号有权限用的模型元数据动态拉回来，统一映射成标准模型 ID 喂给网关的 `/v1/models` 接口。

第三件脏活，也是最考验细节的一步，是流式工具调用（SSE）的字节级格式转换。

像 Codex CLI 和 Claude Code 这种重度依赖工具调用的客户端，对 SSE 流式返回里 `tool_calls` 数据块的事件顺序和索引号检查到了吹毛求疵的地步。但上游私有渠道吐出来的流式分块里，经常把模型的思考过程（Reasoning）、普通回答文本还有工具调用的 JSON 参数碎片混装在自己的私有字段里。

我在插件内部专门写了一个带状态的流式解析状态机。它一边从上游读私有分块，一边在内存里实时拆解，严格按照标准 OpenAI 和 Anthropic SSE 协议的时序规范，把缺失的事件头、块开启标记和递增索引号补得严丝合缝，再实时刷回给网关。

因为我自己平时是在 Mac（`darwin-arm64`）上写代码调试，而本地的主力网关又跑在 OrbStack 的 Linux 容器里，我还给 [**cpa-plugin**](https://github.com/xxkingstuggle/cpa-plugin) 仓库配齐了 `.github/workflows/build.yml` 跨平台交叉编译流水线。每个渠道插件各自维护独立的 `go.mod`，每次构建同时产出 macOS 的 `.dylib` 和 Linux 的 `.so` 动态库，本地测试生成的敏感 Token 凭证文件也全部被 `.gitignore` 死死拦在仓库门外。
