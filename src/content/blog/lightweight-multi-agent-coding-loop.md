先交个底，这篇手记最初写于 2026 年 9 月，记录的是我最早用 `tmux` 和本地状态文件把好几个 CLI 编码工具串起来协同干活的尝试。后来这套土办法一步步长出了骨肉，拆分演进成了后来的 [chatgpt-supervisor-prototype 状态机](/posts/chatgpt-supervisor-state-machine/) 和 [本地多模型网关](/posts/multi-model-gateway-agent-ops/)。

回想 2026 年 9 月那会儿，我之所以非要折腾多 Agent 协同，是被「单模型既当运动员又当裁判员」的毛病给气着了。

平时改个几行的小函数，一个编码助手自己干到底完全没问题。但只要任务稍微大一点，让同一个模型既在前面想方案、又在中间改代码、最后还由它自己来宣布「验收通过」，它十有八九会在最后关头偷懒。有时候测试明明报错了它也不深追，有时候聊着聊着上下文长了，干脆忘了最早定的核心约束，只凭自己嘴上说一句「已完成」就想交差。

我也去翻过市面上当时很火的几个重型多 Agent 编排框架。看了一圈下来，觉得拿它们来跑本地个人项目实在太重了。你为了写个代码，得先在电脑上拉起一堆消息队列、向量数据库和中间件服务，万一哪天环境抽风，排查编排框架本身的耗时比我自己写业务代码还长。

我就想，能不能不用任何重型中间件，只靠每天都在用的终端工具和本地文件，搭一条足够轻、但规矩极其严格的流水线？

这套轻量流水线最核心的死规矩只有一条，负责拆任务和做验收的主管，绝对不准亲自下场替执行者写那部分业务代码。

当时我把桌上的角色分成了三层。我自己在最顶层，只负责跟主管 Codex Desktop 交代最终目标，并在收尾时做总验收；Codex Desktop 坐在中间当铁面主管，负责先摸清仓库结构、把大活儿拆成小任务单，等底下的执行者交活之后，它再亲自去翻文件、查 `git diff`、自己动手跑构建和测试；而真正下场写代码的执行者，则在 AGY（Antigravity CLI）和 Claude Code 之间按需切换，平时日常的局部实现默认交给 AGY，遇到特定硬骨头或者需要换脑子时就切给 Claude Code。

```text
        我（提目标、最终验收）
              |
              v
      Codex Desktop（拆任务、定规矩、验收）
              |
          叫谁来干活
              |
     +--------+--------+
     v                 v
 AGY（默认）      Claude Code（指定/备用）
```

为了让 Codex Desktop 能顺滑地指挥两个不同的 CLI，我给它配了两个薄薄的入口 Skill，一个负责调 AGY，一个负责调 Claude Code。但这两个 Skill 只负责决定「什么时候该叫谁上场」，底下真正管干活的，是同一套共用的任务引擎。

无论是 `tmux` 后台会话创建、进程生命周期管理、超时控制、日志落盘、断点续接、防系统休眠还是 Git 工作区锁，全都在这一套底层引擎里统一处理，彻底省去了把同一套脏活累活维护两遍的麻烦。

那主管怎么知道底下的执行者把活干完了呢？

我绝不靠「去扫一眼哪个源码文件修改时间最新」这种玄学来猜进度。

每一个大目标都会分配一个唯一的 `task_id`，底下的每一轮派工依次编号为 `job-001`、`job-002`，所有的案卷材料整整齐齐地落在 `.agent-work/<task_id>/<job_id>/` 目录里。里面有写清本轮要求的 `prompt.md`，有实时记录输出的 `stdout.log` 和 `stderr.log`，有管理进程自己的 `manager.log`，还有最终封存结局的 `result.json`。

等待任务跑完的方式我也特意做了隔离。执行进程被丢进独立的 `tmux` 会话里跑，跟 Codex 那次工具调用解耦开；本地由一个极轻量的 `waiter` 进程在后台安静地轮询 `result.json`。等待期间不占大模型会话，也不烧半个 Token 的额度。万一中途外层的 Codex Desktop 窗口不小心被我关了，后台的 `tmux` 任务照样稳稳当当地往下跑，重新打开窗口之后，拿 `status`、`wait` 或者 `recover` 带上任务编号就能原地把进度接回来，只有当我明确下达 `cancel` 指令时才会真正终止它。

但这里有一条我踩过坑才立下的铁律，`result.json` 显示进程正常结束，绝对不等于验收通过。

执行者在日志里拍胸脯说「我已经全部改好了」，那只是它自己以为改好了。`result.json` 是由外层管理进程根据进程退出码和日志状态写进去的（执行者自己没有权限篡改这个文件），它只证明「这轮子进程跑完了」，不证明写出来的代码真能跑通。

每次收到 `result.json`，主管 Codex 必须亲自下场验货。先核对 `git status` 和 `git diff` 看它到底动了哪些文件，再亲手跑一遍 `build`、`test` 和 `lint`。

为什么我把验货卡得这么死？因为实战里真踩过几次让我哭笑不得的大坑。

有一次，我派 Claude Code 去修一个模块。它洋洋洒洒给我返回了一大段修改说明，进程也以 `0` 状态码体面退出了。结果我去 Git 工作区一看，居然连一个字节的文件都没变。后来我把调用切到 `stream-json` 模式去扒事件流，逐一核对 `tool_use` 到 `tool_result` 再到 `end_turn` 的闭环，才抓到它那次光在嘴上推演了一遍代码，压根没触发写盘工具。

还有一次更惊险，执行者输出日志太猛，直接把普通进程管道的缓冲区给塞爆了，整个子进程卡在写输出那一步动弹不得。从那以后，我把所有标准输出和错误流全部改成了持续追加写本地文件；而且遇到超时或者取消任务时，绝不只杀最外层的壳进程，而是连着整个进程组（Process Group）一块儿清理，防止底下拉起的编译器或测试子进程变成孤儿僵尸留在内存里。

另外，当执行者交上来的代码没跑过测试、需要打回去返工时，我也严禁主管只丢一句冷冰冰的「测试没过，继续修改」。

你想想看，连人都听不懂「继续修改」到底要改哪儿，更何况是 AI？要求一含糊，执行者九成九会顺着刚才的错误方向继续打补丁，越补越烂。所以返工单必须写清具体的文件路径、当前的错误表现、预期的正确结果，附上报错堆栈或测试断言失败的实锤证据，还要明确标出哪些已经跑通的文件不准乱碰。

也是在跑这套返工循环的时候，我做了一个很痛快的决定，把早期设的「最多返工 6 轮或 10 轮」的死板计数器上限给删了。

早期设上限是怕它死循环烧钱。结果有一次跑大重构，到了第 6 轮结束时，代码只剩最后一个很明确的边角缺陷了，连怎么修的返工说明都已经生成好了，结果计数器啪一下到顶，强行把整个流程掐断在黎明前的一秒。后来我就想通了，只要不是遇到了额度耗尽、认证失效、网络断连或者权限缺失这种硬阻塞，下一轮该不该继续，应该由主管根据 `git diff` 收敛情况和测试结果来定，而不是被一个死板的数字一刀切。

再往后，当终端 CLI 这一层跑顺了，我又往上接了一层浏览器自动化 Skill，把网页版 ChatGPT 请进来当顶层军师。每次 Codex 审完代码写好本地报告，就自动发进专门的会话里请高层定夺下一步，而且要求网页端的回复必须带上严格的协议头和结束标记，格式不对当场拒收并保留原文备查。

回头看 2026 年 9 月折腾的这套早期流水线，它教会了我几个一直沿用到今天的工程习惯，单轮派工的粒度千万别拆太大，最好控制在十几分钟内能跑完验证的规模；同一个 Git 工作树同一时刻只准放一个执行者进去写，真要并行就老老实实拆 Git Worktree；还有最核心的一点，永远不要相信提示词里的口头承诺，提示词管不住的手脚，只能靠 `git diff` 和自动化测试去拦。更多的后续演进工程，也都可以直接在我的 [GitHub 主页](https://github.com/xxkingstuggle) 上翻到。
