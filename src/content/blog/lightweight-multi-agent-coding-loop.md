## 为什么搞这个

现在做项目基本离不开 CLI 编码助手了。但任务一大就会出问题：同一个模型又要想架构、又要写代码、又要自己测试，它很容易糊弄你——写完几百行代码，测试报错了也不细看，直接来一句"已完成"；或者聊得久了，慢慢就跑偏了。

我也看过那些现成的多 Agent 框架，太重。消息队列、数据库、一堆中间件，本地跑起来出一次故障，查环境的时间比写代码还长。

所以我自己拼了一套，规矩就一条：**管事的人不干活，干活的人不管事。**

具体分工是这样：

- **我**：只跟 Codex 说话。提目标，最后验收。
- **Codex Desktop 当主管**：它先摸清项目，拆任务，把"要做什么"写清楚交给执行的人。对方干完，它自己去看文件、看 `git diff`、自己跑构建和测试。执行者说"我做完了"没用，得它自己验过才算。
- **AGY（Antigravity CLI）是默认干活的人**：拿着明确指令写代码，做局部修改。
- **Claude Code 是备胎，也可以指定用**：有些活我想让 Claude 干就指定它；AGY 没额度了、挂了，也换它顶。

```text
        我（提目标、最终验收）
              |
              v
      Codex Desktop（拆任务、定规矩、验收）
              |
          叫谁来干活
              |
     +--------+--------+
     v                 v
 AGY（默认）      Claude Code（指定/备用）
```

## 一套引擎，两个入口

面向 Codex 只有两个 Skill：一个 AGY，一个 Claude Code。它们只管"什么时候该叫谁"，真正干活的底层是同一套引擎。

tmux 会话、进程管理、超时、日志、状态、断点续接、防休眠、Git 锁，全在这套引擎里。不重复写两份，谁被叫起来，行为都一样。

## 怎么知道活干完了

不靠"看哪个文件最新"这种猜法。

每个大目标有一个 `task_id`，每一轮往下排：`job-001`、`job-002`……所有东西都放在 `.agent-work/<task_id>/<job_id>/` 里：

- `prompt.md`：这轮要干什么，写得清清楚楚。
- `stdout.log`、`stderr.log`：执行过程中的日志，边跑边写。
- `manager.log`：管理进程自己的状态记录。
- `result.json`：跑完了的凭据。

中间怎么等，也有讲究：

1. 执行进程在 tmux 里跑，跟 Codex 那次调用完全脱开。Codex 不会一直挂着干等。
2. 本地有个 waiter 在轮询 `result.json`。等待期间不叫模型，不烧额度。**但 Codex Desktop 关了它不会自己醒过来**——这是现在的一个硬伤，后面细说。
3. waiter 断了不等于任务死了。想接着看，用 `status` / `wait` / `recover` 带着 task 和 job 编号接回来；只有明确 `cancel`，才会真的杀进程。

## result.json 不等于验收通过

很多设计里，工人说"我做完了"，上面就信了。这里不行。

`result.json` 是管理进程根据退出码和日志写的，执行者自己改不了。它的意思只是"这个进程结束了"，仅此而已。

**Codex 必须自己验**：看改了什么文件，`git status`、`git diff` 比对，然后真跑一遍 build、test、lint。工人自己的报告，永远不能当成结果。

## 出错得说清楚错在哪

"报错退出了"这种话，等于没说。

引擎把结果分成了几类：正常结束、一般错误、额度用完、认证失效、没权限、超时、被取消、进程崩了、协议坏了。而且"错误类型"和"工作区有没有被改"是分开记的——有的任务报错了但代码是好的，有的则留了半成品。

Codex 要读日志，把真正的原因告诉我，而不是转一句"Agent 报错退出"。之前就吃过这个亏：只告诉我报错，我也不知道该去换代理还是换账号。

## 返工不能只说"继续改"

测试没过，或者做得不对，主管不能就甩一句"继续修改"。含糊的指令只会让模型在错的路上越补越乱。

返工的要求得写全：哪个文件、现在什么表现、应该是什么样、证据是什么（报错、测试断言、diff 片段）、什么不能碰、改完怎么验。

能接着原来的会话就接着，上下文还在；实在接不上了，就让 Codex 重新整理一份简短说明，开个新会话。

## 真踩过的坑

这几个都是实打实撞过的：

**Claude 那边"假装干活"。** 有一次它正常返回了文字，连思考过程都写了，进程也正常退出，但一看 git，一个文件都没动。后来切到 stream-json 模式，盯着 `tool_use → tool_result → end_turn` 这条链有没有真的走完，再加上看工作区文件到底变没变，才不再被骗。

**模型名写死会出事。** 早期把后端模型名硬编码，网关一改映射就 400 报错。还有一次更坑：本地跑着代理软件，它重启的时候把自己的模型来源也断了，工人当场没模型可用。后来就不写死了——Claude 跟着 CC Switch 的配置走，AGY 单独指定。

**管道会堵死。** 工人的输出量很大，普通管道一会儿就把缓冲区撑满，整个卡住。后来改成持续往文件里写。另外超时和取消不能只杀最外层进程，得整个进程组一起杀，不然编译器那些子进程会变成孤儿。

**别让 Mac 睡觉。** 用 caffeinate 防止空闲休眠，但合盖是真的会停，这个不承诺。还有同一个 git 工作区只允许一个人写，开工前留个 baseline 快照，我自己没提交的改动不能被覆盖。

## 把 6 次、10 次的轮数上限删了

一开始怕它无限循环，设了启动次数上限。

结果真干活的时候被它坑了：上一轮结束，还有明确的缺陷，返工的说明都写好了，计数器说到顶了，硬是把任务卡在最后一步。

**所以我把上限删了。** 调用历史照记，下一轮要不要继续，由 Codex 看真实的 diff 和测试结果决定。当然也不是无限跑：额度用完、认证失效、网络不行、权限不够、缺关键信息，这些硬障碍一出现就立刻停，然后明确告诉我。

## 后来又加了一层：让网页版 ChatGPT 当军师

CLI 这层跑顺之后，我又往上加了一环。

我本来有个手动习惯：Codex 审完代码，我把报告复制给网页版 ChatGPT，让它判断下一步该改什么，再把它的回复粘回 Codex。这个来回是有用的，但全靠人肉搬运，任务一长就变成了体力活。

于是我把它做成了一个 Skill：Codex 先读本地现状、写报告，用浏览器发进一个专门的会话。网页的回复必须带协议头和结束标记，只有它明确说"完成了"，而且本地验收证据齐全，任务才算结束。两层保险：发送确认丢了就立刻暂停，不许盲目重发；执行记录缺失的时候，只允许去看真实文件和 diff，不许凭一个标记就"重放"。

这套是真跑通的：在隔离的演示项目里跟网页会话来回三轮，离线测试十项全过。第一轮回复因为格式不对，被本地直接拒收，原文存档。

## 现在的真实边界

说点不好听的，这些问题还没解决：

1. 没跑过两小时以上的无人值守长任务。短任务验证过，长的没试。
2. Codex Desktop 关掉之后，它不会自己醒。现在只能靠那次还没返回的调用撑着，或者手动用命令接回来。
3. Git 锁只管得住这套体系里的工人，管不了我在 IDE 里手动改，也管不了别的进程。
4. 没有系统级沙箱。"别改这个目录"只是写在提示词里的要求，不是真的锁。
5. Git 只能还原仓库里的东西。仓库外的文件、外部接口的调用，快照救不回来。

## 最后

不用搞什么大平台。手边几个 CLI，把规矩定清楚，验收认真做，本地就能搭出一套真能干活的流程。
