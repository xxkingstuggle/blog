最近在连续处理长任务时，我越来越频繁地依赖 CLI 编码助手。但只要任务稍具规模，单 Agent 模式就会暴露出结构性瓶颈：当同一个模型既负责理解全局架构、拆解任务，又负责敲代码、改文件、自我测试时，它极容易陷入“上下文饱和”与“既当裁判又当运动员”的盲区。模型往往会在写完数百行代码后，面对测试中的隐蔽回归草草得出“已全部通过”的幻觉，或在长会话中逐渐偏离既定约束。

市面上的重型多 Agent 框架大多引入了分布式消息队列、复杂数据库与自由度过高的代理间闲聊。在本地落地时，这种架构既沉重又难以排查：一旦任务中断，排查网络拓扑与中间件的成本往往超过了编码本身。

我的诉求非常收敛：**不造庞大平台，不引入分布式依赖，仅基于本地开发环境，将 Codex Desktop、Antigravity CLI（AGY）与 Claude Code CLI 组织成一个具备确定性、可诊断且分工严密的多 Agent 编程闭环。**

这套方案在真实任务里跑过。下面说说它的架构、执行流程、审查返工、踩过的坑，以及现在还做不到的地方。

```text
                  +-----------------------------------+
                  |            用户 (User)            |
                  +-----------------------------------+
                                    | 下达目标与最终验收
                                    v
                  +-----------------------------------+
                  |       Codex Desktop (主管/审核)    |
                  | - 项目勘测与任务切分               |
                  | - 编写高规格 Prompt 交付执行       |
                  | - 独立审查真实 Diff 与自动化测试   |
                  | - 决定接受交付或发起针对性返工     |
                  +-----------------------------------+
                                    |
                    触发 Skill 调用受管引擎
                                    v
                  +-----------------------------------+
                  |          共享 Worker 引擎          |
                  | - tmux 会话隔离与生命周期解耦     |
                  | - waiter 本地等待 (不唤醒 Codex)   |
                  | - Git 工作区排他锁与 Baseline 保护 |
                  | - 持续流式日志、进程组终止、防休眠 |
                  +-----------------------------------+
                                    |
                    +---------------+---------------+
                    |                               |
                    v                               v
         +--------------------+          +--------------------+
         | Antigravity (AGY)  |          |  Claude Code CLI   |
         | 默认执行型程序员   |          | 第二执行者 / 备用  |
         +--------------------+          +--------------------+
```

## 最小架构与双层角色分工

核心原则只有一条：**主管和执行者彻底分开**。

### 1. 角色分工

* **用户与 Codex Desktop（主管与审核者）**：用户始终只对 Codex 下发任务。Codex 负责全局理解、项目检查、架构设计与任务拆分。它为执行者编写详细 Prompt；在 Worker 交工后，Codex 绝不轻信对方自述，而是亲自调用工具检查受影响文件、审查 Git Diff，并实际运行构建与测试，决定是接受成果还是要求返工。
* **Antigravity CLI（AGY，默认执行者）**：AGY 是默认的执行型程序员。它具备代码检索与文件编辑等工具调用能力，专注于在局部受限的上下文中将明确指令落实为代码。
* **Claude Code CLI（第二执行者与备用）**：Claude Code 作为明确指定时使用的第二执行者。当遇到特定逻辑偏好，或者 AGY 遭遇 Quota 耗尽、认证失效、上游服务不可用时，它作为备用执行者接入。

### 2. 共享 Worker 引擎

为避免两套重复实现，面向 Codex 的两个 Skill 仅定义各自的触发条件与主管流程规范。而底层的 tmux 会话管理、Manager 进程、本地 waiter 轮询、Provider 适配器、超时控制、日志记录、状态跃迁、会话续接、进程组终止、`caffeinate` 防休眠以及 Git 工作区锁，全部下沉在共享引擎中。

统一的底层引擎确保了无论调用哪个 CLI，执行时的进程管理、超时捕获与状态报告都保持完全一致的行为准则。

## 确定性通信与 Job 生命周期

通信完全建立在确定的目录结构上，不靠“看哪个文件最新”猜状态。

### 1. 确定性持久目录

系统为每个顶层目标分配一个持久的 `task_id`，而执行轮次使用严格递增的编号：`job-001`、`job-002`……所有输入输出均保存在 `.agent-work/<task_id>/<job_id>/` 目录下：
* `prompt.md`：Codex 传递给 Worker 的完整指令。
* `stdout.log` 与 `stderr.log`：Worker 运行期间的持续流式日志。
* `manager.log`：守护进程状态变迁日志。
* `result.json`：运行结束时的结构化交工凭据。

### 2. 异步生命周期与本地等待机制

```text
Codex Desktop          本地 Waiter            Manager (tmux)          Worker Agent
     |                      |                       |                       |
     |-- 发起 Tool Call --->|                       |                       |
     |   (启动调度并等待)   |-- 拉起 tmux 会话 ---->|                       |
     |                      |                       |-- 启动并监控进程 ---->|
     |   (本地等待阻塞中    |-- 轮询 result.json    |                       | (执行中)
     |    不频繁唤醒模型)   |   (本地无模型开销)    |                       |
     |                      |                       |                       |-- 进程退出
     |                      |                       |<-- 捕获退出码与日志 --|
     |                      |                       |-- 写入 result.json    |
     |                      |<-- 检测到文件写入 ----|                       |
     |<-- Tool Call 返回 ---|                       |                       |
     |   (若中断需显式接回) |                       |                       |
```

1. **脱离主管调用生命周期**：Manager 在 tmux 中启动，执行进程完全脱离 Codex 单次工具调用的短暂生命周期。
2. **本地 Waiter 安静等待**：本地 waiter 脚本只在本地文件系统轮询目标 `result.json`。在等待期间，**严禁每分钟唤醒一次 Codex 模型**，避免在漫长的编译和修改中无谓消耗主管的上下文与调用配额。若存活的 pending tool call 持续有效，waiter 在等待完成后会将精简结果正常返回；但系统并不承诺外部脚本能主动唤醒已关闭或已断开的 Codex Desktop。
3. **断开不杀进程与显式接回**：waiter 中途断开仅仅意味着停止本地等待，绝不会杀死正在运行的 Worker。如果客户端关闭或调用中断，后续必须通过 `status`、`wait` 或 `recover` 带着明确的 `task_id` 和 `job_id` 显式接回现场；只有收到明确的 `cancel` 指令时，Manager 才会向受管进程组发送信号终止执行。

### 3. result.json 是交工单，而非验收结论

在许多设计中，Worker 自称“全部完成”，上层便盲目信以为真。在本架构中：
* `result.json` 由 Manager 根据进程退出码、实际耗时与关键日志特征写入，执行 Agent 自身无权篡改系统终态。
* 它本质上只是一张“交工通知”，证明物理进程已结束。
* **Codex 必须亲自验证**：Codex 收到通知后，必须亲自比对文件修改、检查 `git status` / `git diff`，并在本地实际运行 `build`、`test`、`lint` 或 `typecheck`。Worker 的自述报告永远不能代替真实的命令执行结果。

## 错误必须可诊断

笼统的“报错退出”对工程推进毫无价值。共享引擎将执行结果细分为明确类别：
* `SUCCESS`：正常退出，状态吻合。
* `ERROR`：通用执行错误（如编译报错、测试用例失败）。
* `QUOTA`：API 额度耗尽或限流。
* `AUTH_ERROR`：认证失效或凭证过期。
* `PERMISSION_ERROR`：权限不足或未授权访问。
* `TIMEOUT`：超出单次任务时间上限。
* `CANCELED`：外部显式终止。
* `WORKER_DIED`：进程异常崩溃、段错误或被系统杀灭。
* `PROTOCOL_ERROR`：日志损坏或协议解析失败。

关键在于：**系统将“错误类别”与“工作区改动（working_tree_changed）”解耦记录**。
一个标为 `ERROR` 的任务，其工作区可能完好无损，也可能留有半成品代码。Codex 负责读取 `result.json` 以及 stdout/stderr/provider/manager 的实际日志片段，向用户指出真实故障根因，而不是含糊其辞。

## 独立审计与严密返工

当测试失败或实现偏离时，主管绝不能仅仅发送一句“继续修改”。含糊的指令只会导致模型在原有的错误逻辑上反复修补。

### 1. 返工 Prompt 六要素

Codex 生成的返工 Prompt 必须包含六项刚性内容：
1. **涉及文件**：明确指向有缺陷的具体文件路径。
2. **当前行为**：准确描述当前观测到的错误表现。
3. **正确行为**：阐明符合预期的具体逻辑与契约。
4. **事实证据**：提供测试失败断言、报错堆栈或关键 Diff 片段。
5. **不变量（Invariants）**：明确指出修改时绝对禁止破坏的既有业务逻辑与公共接口。
6. **检查方式与完成条件**：指明 Worker 在退出前必须执行的验证命令，以及判定修复合格的准则。

### 2. 会话恢复与断点接力

在同一工作目标内，系统优先恢复原有的 Agent 会话，保留短期的局部上下文；当检测到会话损坏或连续逻辑发散无法纠正时，则放弃旧会话，由 Codex 提取当前真实状态，整理出简短的 handoff 摘要开启全新的纯净会话。

## 真实工程踩坑与协议适配

真实环境里的多 Agent 协作，坑比预想的多。下面这几条都是真踩过的：

### 1. Claude 兼容路由与 stream-json 校验

在早期使用兼容路由接入 Claude Code 时，曾发生过模型正常返回了文本和思考链（thinking），甚至返回空成功并正常退出，但实际检查 Git 却没有任何文件变动。由于当时无法确证相关事件是在上游模型、兼容协议转换还是路由转发层丢失，系统无法仅凭返回文本判断执行真实性。最终，我们采用原始 `stream-json` 模式，并在日志中对 `tool_use -> tool_result -> end_turn` 链路以及真实工作区文件与终态进行联合校验，避免将未触发工具调用的输出误判为成功。

### 2. 动态模型选择与服务自依赖死锁

早期硬编码后端模型名称时，多次遭遇网关模型映射导致的 400 报错。此外，本地若运行着代理分发软件（如 CPA），一旦该软件因重启刷新自身配置，原本依赖它的 Worker 就会陷入模型断供。最终我们做了解耦：Claude 的模型保持动态，直接跟随用户本地的 CC Switch 配置环境，不硬编码模型别名；AGY 则通过 provider 配置独立指定其执行模型。

### 3. 管道阻塞与进程组治理

Worker 产生的大量终端输出若仅通过普通管道传递，容易迅速撑满内核管道缓冲区导致死锁挂起。引擎通过持续向文件追加流式重定向解决了这一问题。同时，超时和取消逻辑不只杀顶层入口，而是直接向整个进程组（Process Group）发信号，防止编译器等派生子进程变成孤儿进程脱逸。

### 4. 休眠防护与基线保护

引擎使用 `caffeinate` 阻止宿主闲置休眠（Idle Sleep），但文档与流程中明确不承诺合盖（Lid-closed）后继续执行。同时，同一 Git 工作区默认只允许一个写权限 Worker，启动前记录 Git baseline 快照，完整保留人类开发者尚未暂存的既有改动。

## 为什么取消固定轮数硬上限

初期设计中曾设定过 6 次或 10 次的硬性启动轮数上限，用来防止死循环。但在这次实际任务中，这种固定限制遇到了阻碍：当上一轮运行结束、代码仍有明确的真实缺陷且已经生成了具体返工提示词时，固定的启动计数器却机械触顶并阻止了下一轮执行，导致任务在即将收敛时被强行打断。

**因此，我们移除了固定轮数的硬上限。**

但这绝不意味着系统会无休止空转：
* `worker_starts` 和 `launches` 依然逐次记录调用历史，供开发者和主管查验。
* 是否继续推进下一轮，由 Codex 基于真实的 Diff 变化与测试反馈进行判断。
* 遇到真正的硬性阻碍时坚决停机：一旦检测到 Quota 耗尽、认证失效、网络异常、权限越界、关键业务信息缺失或不可恢复的底层环境故障，系统会立刻中断并向用户明确汇报。

## 后来又加了一层：网页版 ChatGPT 当规划者

CLI 这层跑顺之后，我又往上补了一层：让真实网页里的 ChatGPT 会话来当规划者。

起因是我本来就有一个手动习惯——Codex 审完代码，我把报告复制给网页版 ChatGPT，让它判断下一步改什么，再把它的指令粘回 Codex。这个来回有价值，但全靠人肉转手，长任务里很快就变成了重复劳动。

我把它做成了一个 Skill（`chatgpt-supervisor`）：Codex 先读取本地真实现状、生成报告，用真实浏览器发进一个专用会话；网页的回复必须携带严格的协议头和结束标记，只有拿到明确的完成判定、并且本地独立验收证据齐全，任务才算结束。Codex 始终是本地事实、权限与执行的负责人——网页只回答「下一步做什么」和「是否完成」。有两处是我特意加的保险：发送确认一旦丢失立即暂停，不允许盲目重发；执行记录缺失时，只允许核对真实文件与 `git diff`，不允许凭标记「重放」。

它也是真跑通过的：在一个隔离的演示项目里，与网页会话完成了三轮真实往返，离线测试十项全过；第一轮的回复因为协议头不合规，被本地直接拒绝并存档原文，修正协议之后才继续。边界同样写清楚：登录、验证码、配额、页面中断，这些仍旧交回给人。

## 当前系统的真实边界与局限

这套架构现在还有几个绕不过去的边界：

1. **未经超长无人值守验证**：AGY 与 Claude Code 均在隔离 Git 仓库中通过了真实短任务验证，能够正确调用工具并由 waiter 自动把精简结果交回 Codex，共享引擎的本地隔离测试也已通过；但系统尚未在长达两小时以上的复杂无人值守场景中完成验证。
2. **Codex 宿主关闭后的恢复盲区**：如果 Codex Desktop 客户端本身被关闭，自动恢复模型回合缺乏原生保证。目前可靠的路径是等待后台未完成的 pending tool call 正常返回，或在重启客户端后通过 `status`/`wait`/`recover` 显式接回。
3. **工作区锁范围局限**：当前的 Git 排他锁仅能约束受管体系内的 Worker，无法阻止开发者在 IDE 里手动修改或其它外部进程并发写入。
4. **缺少物理沙箱隔离**：Prompt 中的路径修改禁令属于软约束。在没有操作系统级沙盒支持下，它不是强制的安全屏障。
5. **非 Git 资产不可逆**：Git baseline 仅能追踪受管仓库内的文件变动。外部 API 调用、仓库外的全局配置文件修改以及逃逸的外部服务，都无法通过版本库快照完全还原。

## 可复用设计原则

折腾下来，我觉得有四条经验可以复用：

1. **主管重审查，工人重执行**：将宏观规划与微观实现剥离，坚持由主管做最终的真实验收，避免执行模型对未经验证成果的自我认可。
2. **物理事实优于模型自述**：用确定的文件目录、退出码、落盘日志与真实的 `git diff` 驱动流转，不凭模型输出的自然语言做流程裁决。
3. **审计必须依托真实构建**：没有经过实际运行并通过的测试与构建，一切所谓的“已完成”都只是未经验证的猜测。
4. **共享治理下沉，错误归因透明**：把进程控制、管道流式化、超时管理等通用基础设施沉淀为底层引擎，并将退出原因与现场改动解耦呈现。

不用上什么大平台。手边几个 CLI，加上清楚的规矩和真实的验收，本地就能搭出一套靠得住的多 Agent 流程。
