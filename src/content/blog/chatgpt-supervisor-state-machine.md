遇到那种跨好几个模块的大重构，或者一跑就是两三个小时的硬骨头任务时，我特别喜欢用一种「双脑配合」的姿势干活。

在浏览器里开着网页版 ChatGPT，让它站在高处帮我审架构、推演下一步该怎么改；而在本地终端里跑着 Codex CLI，让它当手脚麻利的执行官，实打实地改代码、跑测试。

听起来配合得挺美，对吧？

刚开始我也是这么觉得的，全靠自己一双手在浏览器和终端两个窗口之间来回复制粘贴。

结果连着跑了几次长任务之后，我被三个低级但致命的错误折腾得没脾气了。

第一个坑是「上下文错位」。任务跑到下午，本地代码明明已经改到第 4 轮了，我切窗口复制的时候手滑了一下，发给网页端 ChatGPT 看的居然还是第 2 轮留下的旧报错。两边脑子不在一个时空里，拿回来的修改指令往当前代码上一套，当场全乱了。

第二个坑是「多终端踩踏」。有时候上一个终端窗口里的 Agent 正在跑一个耗时好几分钟的集成测试，我等得走神了，忘了它还在跑，顺手又在旁边新开了一个终端窗口发指令。两个 Agent 同时往同一批源码文件里写代码，直接把工作区踩成了烂泥。

第三个坑最气人，叫「报喜不报忧」。本地 Agent 跑完一轮改动，日志只轻飘飘地给我总结了一句「已修复」，把底下真正关键的命令退出码和两条没跑通的边缘测试悄悄咽了下去。我拿着这句假捷报去问网页端下一步，后面的决策全建立在流沙上。

被坑了三回之后，我决定不能再靠人肉剪贴板当传令兵了。我用纯 Python 3 标准库写了一个叫 [**chatgpt-supervisor-prototype (v0.1.0)**](https://github.com/xxkingstuggle/chatgpt-supervisor-prototype) 的状态机 CLI，在网页端军师和本地执行官之间立了一道铁规矩。

这套 `supervisor.py` 的核心想法其实特别直白，就是在本地任务目录里维护一个严格的文件状态机。所有的动作必须老老实实按顺序走完六个状态阶段，谁都不准跳步。

```text
[draft] ──► [awaiting_chatgpt] ──► [instruction_ready] ──► [executing]
                  ▲                                             │
                  └─────────── (提交执行报告，进入下一轮) ─────────┤
                                                                ▼
                                                [paused / completed / failed]
```

你看这张流转图。当状态停在 `awaiting_chatgpt` 的时候，说明本地这一轮的现场报告已经打包封存好了，正在等网页端的高层指令；在这个节骨眼上，本地的 Codex 是绝对不准擅自去碰代码的。

只有当高层回复的指令被写进文件、校验通过，并把状态正式推进到 `instruction_ready` 之后，本地执行器才有资格领锁干活。而在 `executing` 执行期里，系统拒绝任何新指令半路插队，必须等当前这轮老老实实跑完、交上完整的执行报告并把锁还回来，才能开启下一轮循环。

光有状态图还不够，要是两个终端窗口同时去改同一个状态文件怎么办？

为了彻底防住多进程并发搞乱现场，我在 CLI 里连上了三把锁。

第一把锁是 `state_version` 乐观锁比对。每次任何一方想修改状态 JSON，命令参数里必须带上自己刚才读到的 `expected_state_version`。比方说现在状态文件已经是版本 `3` 了，CLI 核对一致后才会把它升到版本 `4`，并通过同目录临时文件原子替换（Atomic Rename）落盘。如果旁边某个忘关的过期窗口还拿着版本 `2` 的老黄历过来想改状态，CLI 当场就会报错把它顶回去。

第二把锁是执行期的独占互斥锁 `lock_token`。本地 Codex 真正开始改代码之前，必须先调 `acquire-lock` 领走一个随机生成的 `lock_token`。在它交出最终报告释放这把锁之前，任何其他进程来要锁都会吃闭门羹。

这里我做了一个很反直觉、但救了我好几次的设计，我特意没有做「超时自动作废抢锁」。

为啥不设超时自动抢锁呢？你想想看，在本地跑一次完整的全量编译或者 Playwright WebKit 几何回归测试，动不动就要好几分钟。如果你简单粗暴地设个 60 秒超时自动解开锁，前一个进程明明还在吭哧吭哧跑构建，第二个进程一看超时就直接闯进来改文件，那整个构建现场瞬间就炸了。所以真要是遇到进程意外崩溃留下了死锁，规矩就是必须由人先确认后台进程确实不在了，再显式执行 `recover-lock` 接管。

第三把锁则是交接文档的 SHA-256 哈希绑定。每一轮发给 ChatGPT 的现场报告（Request Packet）和 ChatGPT 发回来的指令（Instruction Packet），都会单独存成编号清晰的 Markdown 文件，并且在 `state.json` 里死死绑住它们的 SHA-256 摘要，哪怕文件被人手滑多敲了一个空格都能立刻抓出来。而且发给 ChatGPT 的报告模板里，我用硬校验要求必须附上真实的 `git status`、改动文件清单、实际跑过的验证命令以及原始退出码，彻底断了 Agent 只写一句「已经修好了」糊弄过关的念头。

为了让这个小工具不管拷到哪台开发机还是容器里都能开箱即用，整个 `supervisor.py` 没有引入任何一个第三方 pip 依赖，纯靠 Python 3 标准库写成。仓库里的 `tests/test_supervisor.py` 严严实实测了正常流转、非法跨阶段报错、版本号 CAS 冲突、互斥锁争用以及文件哈希篡改这 10 种核心场景。源码和配套打包好的 Skill 我都已经发在了 [chatgpt-supervisor-prototype v0.1.0 Release](https://github.com/xxkingstuggle/chatgpt-supervisor-prototype/releases/tag/v0.1.0) 上。
