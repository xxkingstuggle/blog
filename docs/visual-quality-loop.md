# MYZJX 前端视觉质量闭环（v1）

## 目标与边界

这是现有 Astro 站的视觉验收层，不是重做框架、统一重写 CSS，也不是一份命令 AI「做得高级」的提示词。

- 网站类型：求职展示型个人作品集。访客应能快速看到真实软件、项目能力、可信的内容和联系方式。
- 发布原则：不修改 `main`、不合并、不发布生产，直到项目负责人认可真实截图和交互。
- 只调整本次任务明确要求的页面与组件；不得顺手修改 Worker、D1、鉴权、真实软件状态或文章事实。
- 采用已有 `src/styles/tokens.css`、`GalleryCard.astro` 等组件，不为同一效果叠加第 2 套样式或新的全局动画。
- 文档是意图和验收协议；结构、检查工具和可复现证据比反复叮嘱更可靠。

## 1. 固定结构（硬约束）

| 目标 | 实现或已有保护 | 验证 |
|---|---|---|
| 媒体按原比例显示 | `GalleryCard.astro` 的图像元数据与媒体舞台，只有外壳+内层 2 层圆角 | `scripts/verify-studio-webkit.mjs` 图片位置与几何断言 |
| 动效只在局部发生 | `cloth-pressure.ts`，不得增加全局跟随黑影、彩色鼠标尾迹、无限 RAF | WebKit 鼠标移动、离开回弹断言 |
| 真实内容与项目状态 | `src/lib/software.ts` 和文章集合是事实来源 | 相关单测与页面检查 |
| 可用性 | 桌面/320px/390px、深浅色、键盘/触摸、减少动态效果 | WebKit 断言与截图 |
| 性能 | 优先原生 CSS、按需媒体加载、不增加无意义的高成本滤镜 | 构建、媒体预算和必要时现场性能实测 |

**禁止把「审美不好」伪装成客观自动测试**；不能仅靠 lint 判断留白是否舒服或动效是否有质感。

## 2. 视觉方向（软约束）

- 关键词：年轻、克制、精密、有实验精神；真实内容与可用性 > 性能 > 交互质感 > 装饰。
- 信息层级：第一屏传达「是谁 / 做过什么 / 作品在哪里」，不要重复展示同一素材，不引入多余的 A/B 作品标签。
- 作品媒体：图片或视频决定容器比例，内容边到边；软件作品优先真实截图，缺图时用真实文字与排版，不用假产品图。
- 指针反馈：默认鼠标自然无额外阴影；移动到卡片时只让接触处有轻微凹陷或形变，离开后平顺恢复。
- 细节标准：不同页面有统一的字体、空间、色彩与操作反馈，但不能为了「统一」牺牲真实内容的自然比例。
- 对优秀网页参考，只移植明确的交互机制；不得把未经讨论的视觉方案当成用户批准的设计。

每个视觉需求先写清楚：**参考样本 / 希望复现的机制 / 不允许出现的效果 / 真实页面证据**。对审美分歧保留两种对比方案，不在提示词里反复争论形容词。

## 3. 单 Agent 内循环（先跑稳这一层）

1. **接任务**：指出要改的 1 个视觉问题及其页面、设备和现象。先检查现有 CSS、组件和历史同类尝试。
2. **做一个小改动**：优先复用设计 Token、已有组件，不同时改排版、配色和鼠标动画三个维度；删除失效的旧规则。
3. **跑硬检查**：`npm ci`（首次）、`npm run check`、`npm test`、`npm run build`，以及已有 WebKit 真实渲染检查。失败先定位修复。
4. **收集证据**：安装已有 CI 使用的 Playwright WebKit 后运行 `node scripts/collect-visual-evidence.mjs`。脚本自己启动本地预览，生成固定视口的截图、鼠标交互视频、`checks.json` 和 `REVIEW.md`；**不需要反复调用 Vercel 构建**。
5. **看证据修正**：Agent 必须阅读自己的截图、分析录像与交互；若没有图像检查能力，应明确说尚未审查，不得只凭测试绿灯声称审美达标。
6. **请求人工判断**：把新的截图与选定的参考图、上一次版本放在一起；负责人对美感、动效的最终取舍进行确认。
7. **沉淀重复错误**：同一问题出现两次，优先修改组件、lint、可复现测试或交付验收，而不是仅往 `AGENTS.md` 叠加文字。

只有内循环能稳定完成一个卡片或一个页面的改动后，才考虑用外循环接收需求、创建任务、派多个 Agent 并行。

## 4. 验收证据和判定

`scripts/collect-visual-evidence.mjs` 当前固定输出：

- 首页：1440px 深浅模式；390px 深浅模式；320px 亮色。
- 软件列表、USBLinkMic 软件详情、思路导航文章页、手机关于页。
- 鼠标交互：移动前、按压中、离开后截图及 `hover-motion.webm` 完整录像。
- 自动诊断：可见文档宽度是否超出视口、已加载图片是否损坏、JS 未捕获异常。

**硬门槛**：构建、已有测试、对应设备适配与功能不能倒退；若本次改了关键行为，补充可机器判定的回归测试。

**审美门槛**：负责人看过相同视口、相同状态的实际图像／录像，才可标记为 `APPROVED`。当前脚本永远只生成 `PENDING`，避免 Agent 给自己发合格证。

**不要误判**：
- 截图像素变化只说明「变了」，不说明「更好」。Playwright 像素基线适合保护已批准的稳定设计，不适合自动决定新设计是否高级。
- 视频或截图无法单独证明 60 FPS、LCP、INP、CLS；性能需单独测量并交代设备和方式。
- Headless WebKit 不等于真实 iPhone Safari；上线前的真实设备体验仍需确认。
- 没有运行测试时，不能写「PASS」；没有实际看到截图时，不能写「视觉已通过」。

## 5. 执行命令

```bash
npm ci
npm run check
npm test
npm run build
# 已安装 Playwright 及其 WebKit 浏览器之后：
node scripts/collect-visual-evidence.mjs
# 也可针对已有的独立预览网址收集证据，不启动本地站：
VISUAL_REVIEW_URL=https://your-preview.example node scripts/collect-visual-evidence.mjs
```

证据在 `artifacts/visual-review/REVIEW.md`。GitHub Actions 的 WebKit 工作流在 PR 上自动收集并上传证据，不会因此自动批准或发布生产。
